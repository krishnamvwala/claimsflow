# ClaimsFlow Source-Data Contracts

**Document status:** Baseline draft

**Blueprint phase:** Phase 0 - Discovery and Success Contract

**Data boundary:** Synthetic portfolio data only

## 1. Purpose

These contracts define the exact source interfaces that ClaimsFlow version 1 may ingest. They convert the source assumptions in the [requirements](../requirements.md) and the observable conditions in the [acceptance criteria](../acceptance-criteria.md) into machine-readable schemas for ingestion, validation, lineage, reconciliation, synthetic fixture generation, and downstream modeling.

The YAML files under [`contracts/source-data`](../../contracts/source-data) are authoritative. This document defines the shared rules that apply to all eight contracts.

See [source-contract examples](examples.md) for an illustrative manifest, connected synthetic record chain, validation outcomes, and correction flow.

## 3. Required delivery envelope

Every delivered file must satisfy this interface before row processing begins:

- Data is generated by an approved ClaimsFlow synthetic generator or fixture set and is linked to a provenance-manifest entry.
- Format is RFC 4180-compatible CSV with a header row, UTF-8 encoding, comma delimiter, LF line endings, and no compression in version 1.
- File names follow the pattern declared by the applicable YAML contract. All timestamps in file names use UTC.
- Dates use `YYYY-MM-DD`; timestamps use ISO 8601 UTC ending in `Z`.
- Decimal values use a period, no currency symbol or thousands separator, and at most two fractional digits unless a contract states otherwise.
- Booleans are lowercase `true` or `false`.
- Null is an empty field. Literal values such as `NULL`, `N/A`, and `unknown` are not null.
- Undeclared columns, missing headers, incorrect order, invalid encoding, and contract-version mismatches follow the [validation policy](validation-policy.md).
- Every file has a SHA-256 checksum calculated before ingestion. The pair of source identity and checksum is used for duplicate-delivery detection.

Each file is accompanied by a delivery-manifest record with this exact metadata:

| Field | Type | Rule |
| --- | --- | --- |
| `delivery_id` | STRING | Non-null UUID supplied once for the delivery |
| `source_system` | STRING | Approved synthetic source configuration; added to every ingested row |
| `contract_id` | STRING | Must match one registry contract |
| `contract_version` | STRING | Compatible semantic version used to parse the file |
| `dataset_name` | STRING | Required for reference-data deliveries; otherwise empty |
| `source_file_name` | STRING | Must match the contract file pattern |
| `source_file_checksum_sha256` | STRING | Lowercase 64-character SHA-256 digest |
| `source_extract_at` | TIMESTAMP | UTC extract instant |
| `delivered_at` | TIMESTAMP | UTC delivery instant, not before `source_extract_at` |
| `declared_record_count` | INTEGER | Non-negative number of data rows, excluding the header |
| `declared_control_totals` | STRING | Canonical JSON object containing every amount named by the contract reconciliation section |
| `synthetic_generator_id` | STRING | Approved generator or fixture-set identifier |
| `synthetic_generator_version` | STRING | Immutable generator/fixture version |
| `synthetic_seed` | INTEGER | Reproducible non-secret seed |
| `sequence` | INTEGER | One-based sequence within source, entity, and extract time |

The manifest is validated before the file enters project-managed storage or processing. Manifest `source_system` is authoritative; source CSV schemas therefore do not repeat it.

## 4. Ingestion-added lineage envelope

Source files do not supply the following fields. ClaimsFlow adds them from the verified manifest or ingestion process without changing the source payload:

| Field | Type | Rule |
| --- | --- | --- |
| `batch_id` | STRING | Non-null UUID assigned once per accepted delivery and stable through the run |
| `source_system` | STRING | Approved synthetic source identifier declared by the delivery configuration |
| `source_file_name` | STRING | Exact delivered object name |
| `source_file_checksum_sha256` | STRING | Lowercase 64-character SHA-256 digest |
| `source_row_number` | INTEGER | One-based physical data-row number, excluding the header |
| `source_record_id` | STRING | Deterministic value built from the contract's declared source-record fields |
| `source_extract_at` | TIMESTAMP | UTC source extract time parsed from delivery metadata |
| `ingested_at` | TIMESTAMP | UTC time the raw row was registered |
| `trusted_published_at` | TIMESTAMP | Immutable first UTC instant when this exact source version became eligible for trusted metrics; null until successful publication |
| `contract_id` | STRING | Immutable contract identifier from this registry |
| `contract_version` | STRING | Semantic version used to parse the row |
| `raw_payload_hash_sha256` | STRING | Stable hash of the canonical source-shaped row |
| `processing_status` | STRING | `registered`, `validated`, `published`, `quarantined`, `rejected`, `failed`, or delivery-level `duplicate_no_op` |

`(batch_id, source_row_number)` must be unique. Every raw and trusted record must retain a non-null path through these fields to exactly one registered delivery and original source row. Raw payload values and hashes are immutable; verified corrections create new audit evidence and never overwrite raw evidence. A published row has exactly one immutable `trusted_published_at` not earlier than `ingested_at`; historical calculations use that timestamp to decide what evidence was knowable at their cutoff.

## 5. Type system

| Contract type | Meaning |
| --- | --- |
| `STRING` | UTF-8 text; leading/trailing whitespace is invalid unless a normalization rule permits trimming |
| `INTEGER` | Signed whole number serialized without decimals |
| `NUMERIC(18,2)` | Exact decimal monetary value with two fractional digits |
| `NUMERIC(9,4)` | Exact rate or percentage expressed as a decimal fraction |
| `DATE` | Gregorian calendar date in `YYYY-MM-DD` |
| `TIMESTAMP` | ISO 8601 UTC instant ending in `Z` |
| `BOOLEAN` | Lowercase `true` or `false` |
| `STRING_LIST` | Pipe-delimited ordered list of strings; empty field means no values |

Contract `required` means the column must exist. Contract `nullable: false` means every row must contain a value. A required nullable field therefore must be present but may be empty when the stated business condition allows it.

## 6. Identity, relationship, and history rules

- Natural keys are evaluated after only the approved deterministic normalizations in the validation policy.
- A duplicate natural key within a file is invalid. An identical accepted source-identity/checksum replay receives the delivery-level `duplicate_no_op` status and stops before rows are processed or republished. A key repeated across different deliveries is a new source version only when its declared update timestamp or submission sequence advances. The version discriminator is `source_updated_at` for incremental record contracts and `valid_from` for reference data; claim and claim-line submission sequences are already part of their natural keys. The same natural key and version discriminator with a different payload hash is a collision under `DQ-CMN-011`; the batch is blocked and neither payload is overwritten.
- An `exact_key` relationship maps its source fields, in order, to every field in the target contract's natural key, including lineage-envelope fields such as `source_system`. Required exact-key relationships resolve to exactly one parent; optional compound keys must be either entirely empty or resolve to one parent.
- An `effective_at` relationship maps its source fields to the complete reference business key and uses `as_of_field` to require exactly one version where `valid_from <= as_of_field < valid_to`, treating empty `valid_to` as current. When a TIMESTAMP as-of field targets DATE validity boundaries, the relationship must declare `as_of_conversion: utc_date`; lookup uses the timestamp's UTC calendar date after timestamp normalization. Reference business identifiers are conformed across delivery sources; overlapping or duplicate effective versions are invalid.
- List relationships apply the same effective-date rule to every list member.
- Claims link to a unique eligibility response by source system and eligibility ID. The response must match patient, payer, and plan, be confirmed active, and cover the complete service interval.
- Missing required claim, patient, payer, denial, payment, or appeal identity is never inferred.
- Reference records use half-open validity intervals: `valid_from` is inclusive and `valid_to` is exclusive; empty `valid_to` means current.
- A replay or backfill must use the same contract version originally recorded unless a reviewed migration explicitly authorizes another version.

## 7. Reconciliation rules

Every processable batch records raw, accepted, accepted-with-warning, quarantined, and rejected counts. The four record dispositions must equal the raw count with no unexplained records. An identical duplicate delivery records `duplicate_no_op`, creates zero new raw rows, and is excluded from the record-disposition equation.

Financial source families additionally record the contract-declared control totals. Exact equality is required for source-to-raw reconciliation. Source-to-curated reconciliation uses the signed transaction convention and tolerance later governed by the metric dictionary; until that artifact is approved, the contract default is an absolute variance of `0.00` USD.

Replays compare complete business-key sets, stable record hashes, row counts, and financial totals. Matching totals alone do not prove idempotency.

## 8. Contract versioning and ownership

- Contract versions use semantic versioning.
- Patch: clarification with no parsing or business-behavior change.
- Minor: backward-compatible optional field or allowed-value addition.
- Major: required-field, key, type, grain, comparator, or semantic change.
- A material change requires a reviewed documentation or architecture decision update under `NFR-MNT-004`.
- Business owner: Revenue Cycle Operations.
- Technical owner: ClaimsFlow Data Engineering.

## 10. Definition of done

This artifact is ready for baseline approval when:

- Exactly eight unique source-family contracts parse successfully.
- Every contract declares an exact grain, delivery interface, natural key, source-record identity, schema, validation rules, reconciliation behavior, freshness expectation, ownership, and synthetic-only boundary.
- Every natural-key and source-record field exists in its declared schema or the shared lineage envelope.
- Every direct relationship contains the complete target natural key; every effective-dated relationship contains the complete reference business key, an as-of field, and valid cardinality.
- Every cited requirement maps to its exact primary acceptance criterion in the acceptance matrix.
- Every contract declares a reproducible synthetic fixture profile with baseline volume and required edge cases.
- Every rule identifier is globally unique and its severity/disposition pairing follows the validation policy.
- All relationship targets resolve to a declared source family or reference dataset.
- The automated validator passes.
- No contract permits real patient or customer data or silent correction of ambiguous values.
